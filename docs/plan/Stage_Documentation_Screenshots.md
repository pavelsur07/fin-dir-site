# Скриншоты в базе знаний

## Цель

Редактор добавляет несколько скриншотов к статье за один сеанс. Читатель видит
снимки рядом с шагами инструкции и может открыть их в полном размере.
Агент загружает подготовленный файл через операторскую команду и вставляет его
в Markdown черновика через действующий MCP stdio.

Первый материал для переноса — скриншот формы регистрации в статье
«Главная документации». Сейчас статья ссылается на PNG, размещённый
в каталоге статики на сервере. Общий Markdown-рендерер оставляет от изображений
только альтернативный текст. [Форма регистрации](https://app.vashfindir.ru/register)

Риск реализации высокий из-за приёма бинарных файлов, публичной раздачи и
границы между черновиком и опубликованной статьёй.

## Формат и хранение

- Владелец снимка — одна статья модуля `Documentation`. Редактор сперва
  сохраняет статью, затем загружает файлы и размещает их в тексте.
- В Markdown сохраняется `![Форма регистрации «Ваш Финдир»](doc-image:<uuid>)`.
  Для каждой вставки редактор задаёт короткий содержательный alt. Порядок
  снимков меняется обычным редактированием Markdown. Инструкция в тексте
  остаётся достаточной для выполнения шагов. [W3C](https://www.w3.org/WAI/tutorials/images/informative/)
- Symfony хранит нормализованные байты в отдельной таблице
  `documentation_image` существующей PostgreSQL. Метаданные включают UUID,
  ID статьи, SHA-256, ширину, высоту, размер в байтах, время загрузки и признак
  использования в сохранённом тексте. Внешний ключ закрепляет владельца,
  уникальная пара «статья + SHA-256» защищает от дублей. Списки и страницы
  выбирают метаданные отдельной проекцией. [PostgreSQL 17](https://www.postgresql.org/docs/17/datatype-binary.html)
- Одна база даёт согласованный backup статьи и её файлов через штатный
  `pg_dump`. Для оценки масштаба тысяча снимков по 100 КиБ займёт около
  98 МиБ полезных данных. После начала регулярных загрузок измерять объём
  изображений, длительность backup/restore и время ответа раздачи.
- Предлагаемые стартовые лимиты на один файл: PNG или WebP, до 8 МиБ на
  входе, до 4096 px на сторону и до 8 мегапикселей. Хранить статичный WebP
  без потерь размером до 2 МиБ. Это сохраняет мелкий текст интерфейса.
  Снимок, выходящий за пределы, можно обрезать до рабочей области или
  разделить по шагам. [Symfony Image](https://symfony.com/doc/current/reference/constraints/Image.html)
- Рендеринг остаётся в Symfony/Twig. HTML из Markdown фильтруется. Для
  отрисовки картинки допустим только UUID из набора вложений текущей статьи.
  URL и размеры подставляет сервер. Предпросмотр и публичная страница
  используют общий способ разметки с отдельным разрешением URL по правам.
  [CommonMark](https://commonmark.thephpleague.com/2.x/security/)

## Этап 1. Приём файла и учёт вложений

- [ ] Добавить аддитивную миграцию, `Documentation/Entity/DocImage.php` и
  `Documentation/Repository/DocImageRepository.php`. Добавить индекс списка
  по `page_id, created_at, id`. Проверить преобразование Doctrine BLOB в
  `bytea` и обратное чтение байтов на реальной тестовой PostgreSQL.
- [ ] Добавить `Documentation/Adapter/DocImageNormalizer.php`. Проверять
  размер и фактический формат по содержимому, размеры до декодирования,
  успешное декодирование и выходной WebP. Перекодировать пиксели без
  исходных метаданных. Добавить PHP GD с поддержкой PNG/WebP в dev и
  production CLI/FPM и проверку кодека в `scripts/check-php-runtime.php`.
  [PHP GD](https://www.php.net/manual/en/book.image.php)
- [ ] Добавить `Documentation/Service/DocImageUploader.php` с одним
  сценарием загрузки для Admin и CLI. Проверять и нормализовать файл
  до транзакции. Повторно проверять существование и допустимое состояние
  статьи, искать по SHA-256 и сохранять через `DocWriteTransaction`.
  При повторной загрузке вернуть существующий UUID. Загрузка файла сама
  по себе не правит Markdown, статус или версию статьи.
- [ ] Проверить повреждённый файл, неподдерживаемый формат, каждый лимит,
  откат транзакции, повтор и параллельную загрузку одного файла.
  Ожидание для дублей — одна запись и один UUID в обоих ответах.

## Этап 2. Встраивание и правила доступа

- [ ] Расширить `DocMarkdownProcessor` анализом узлов изображений до их
  фильтрации. Передать в `Shared/Adapter/MarkdownRenderer.php` разрешённые
  изображения как явную опцию конкретного вызова. Сохранить текущее
  поведение всех вызовов без этой опции, в том числе в «Газете».
- [ ] В `DocPageContentEditor` сопоставить UUID со вложениями статьи
  и сохранить признаки использования в той же транзакции, что и текст.
  Неизвестный или чужой UUID и пустой alt дают понятную ошибку. Повтор
  одного UUID в нескольких местах статьи допустим. Проверку готовности
  подключить к `DocPublicationRules` для Admin и `docs_validate_page`.
  Ошибки MCP возвращать в существующих полях `code` и `message`.
- [ ] Ввести отдельные публичный и административный Query и маршруты
  раздачи без расширения файла:
  `GET /media/documentation/{uuid}` на `docs.vashfindir.ru` и
  `GET /admin/docs/images/{uuid}` с `ROLE_ADMIN`. Публичный маршрут выдаёт
  снимок только при наличии ссылки в сохранённом тексте опубликованной
  статьи. Для остальных случаев отвечает `404`. Admin выдаёт снимки
  с `private, no-store`, включая загруженные, но ещё не вставленные.
- [ ] Для публичного ответа использовать `image/webp`, `nosniff`,
  ETag по SHA-256 и `public, max-age=0, must-revalidate`. Проверять
  видимость до обработки условного запроса. После снятия статьи
  с публикации прежний ETag не должен давать `304`. Ответы `404`
  не кешировать, чтобы повторная публикация сразу вернула доступ.
  Публичные запросы не стартуют сессию.
- [ ] Связать проекции с `PublicDocPageQuery`, `AdminDocQuery` и
  текущими проекциями MCP. В статье и Admin preview выводить адаптивный
  `img` с подтверждёнными `width`, `height` и alt. Поддержать
  открытие полноразмерного файла обычной ссылкой и отложенную загрузку
  снимков ниже первого экрана. MCP выдаёт HTML и URL, байты изображения
  запрашивает браузер. [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img)
- [ ] Проверить черновик, публикацию, снятие с публикации и удаление
  ссылки из опубликованного текста. Проверить прямой URL, условный GET,
  доступ без сессии, редактирование Admin и MCP‑предпросмотр с каждым
  профилем чтения. Старые статьи и обычные Markdown-ссылки сохраняют
  прежний результат.

## Этап 3. Рабочее место редактора

- [ ] Добавить панель «Скриншоты» в редактор сохранённой статьи.
  В панели есть множественный выбор файлов, результат по каждому файлу,
  миниатюра и действие «Вставить в текст». Отправлять по одному файлу,
  сохранять несохранённый Markdown и позволять повторить конкретную
  неудачную загрузку. При вставке запрашивать alt и добавлять Markdown
  в позицию курсора.
- [ ] Добавить `POST /admin/docs/pages/{id}/images` для загрузки и
  `POST /admin/docs/pages/{id}/images/{uuid}/delete` для удаления.
  Оба маршрута проверяют `ROLE_ADMIN`, CSRF и принадлежность вложения
  статье там, где передан UUID. Без JS оставить отдельную форму
  загрузки и текст для копирования. Серверные сообщения указывают
  файл и причину отказа.
- [ ] Добавить пагинируемый список вложений статьи по 20 файлов,
  новые первыми. Помечать, какие используются в сохранённом тексте.
  Получать байты миниатюр по мере прокрутки.
  Замена — загрузка нового снимка и редактирование ссылки. Удаление
  неиспользуемого файла выполняется по подтверждённому POST.
  `DocImageRemover` проверяет использование в `DocWriteTransaction`,
  чтобы конкурентное сохранение не оставило битую ссылку.
- [ ] Проверить загрузку нескольких файлов с частичной ошибкой,
  повтор, дублирование, вставку, замену и удаление. Проверить отказ
  без CSRF, запрет удаления используемого файла и гонку с сохранением.
  Браузерные проверки включают клавиатуру, режим без JS, основной
  предпросмотр и ширины 320, 375, 768, 1024 и 1440 px.

## Этап 4. Рабочий процесс через MCP stdio

- [ ] Добавить `Documentation/Command/DocImageImportCommand.php`,
  `app:docs:image:import --page=<id>`. Бинарный файл читается из stdin
  с ограничением размера. Команда доступна локальному оператору и
  принимает только черновик. Сервис загрузки повторно проверяет статус
  под блокировкой. В stdout возвращать JSON с `id`, `mimeType`, `width`,
  `height` и `markdownDestination` со значением `doc-image:<uuid>`.
- [ ] Добавить Makefile-обёртки `documentation-image-import` и
  `documentation-image-import-production` с параметром `DOC_PAGE_ID`.
  Пример вызова: `make -s documentation-image-import DOC_PAGE_ID=1 < screenshot.png`.
  Production использует CLI-образ текущего SHA с той же проверкой реплик,
  что `documentation-mcp-production`. Файл идёт отдельным потоком.
  Лимит MCP в 1 МиБ и полномочия внешнего HTTP MCP сохраняются.
- [ ] Описать цепочку в `README.md`: импортировать файл, получить версию
  черновика через `docs_get_page`, вставить Markdown через
  `docs_update_draft`, проверить `docs_validate_page` и
  `docs_preview_page`. Публикация остаётся действием редактора в Admin.
- [ ] Проверить команду и протокол на изолированной БД. Пустой, превышающий
  лимит вход, отсутствующая и опубликованная страницы дают ошибку без
  вложения. Повтор импорта возвращает тот же UUID. Реальный MCP-клиент
  успешно вставляет и перечитывает Markdown, а его текущие схемы и лимиты
  продолжают проходить протокольные тесты.

## Приёмка и выпуск

- В Admin и через операторский импорт проверена загрузка нескольких снимков.
  Они отображаются в нужном порядке в браузерном предпросмотре и в
  опубликованной статье. Внешние ссылки и текст инструкции работают.
- Изображение из черновика и неиспользуемое вложение недоступны публично.
  Снятие с публикации закрывает выдачу изображения, включая запрос
  со старым ETag. Восстановление тестового дампа возвращает Markdown,
  метаданные и байты снимков с теми же SHA-256.
- Точечные проверки: `make test CMD="--filter 'DocImage|DocMarkdownProcessor|DocMcp|PublicDocumentation|AdminDocumentation'"`.
  После изменений в UI запустить сборки `make website-assets` и
  `make admin-assets` и обновить соответствующие версии по правилам зон.
  Перед передачей в релиз запустить `make documentation-browser-check`,
  `make admin-browser-check`, `make ci`, `make php-runtime-check`,
  `make php-production-build` и `make php-production-smoke`.
  Проверить дамп и реальное восстановление через
  `make site-database-backup-check DOC_BACKUP_WITH_APPLICATION=1`.
  Этот режим применяет миграции приложения и проверяет восстановление вложения.
- Выполнить независимое ревью проверки видимости, обработки файлов,
  конкурентных изменений и миграции. Изменения production-образов и
  выпуск выполняются после отдельного подтверждения по Production Gate.
- Перед выпуском проверить backup. После аддитивной миграции и раскатки
  загрузить проверенный скриншот формы регистрации и встроить его в
  «Главную документации». Для опубликованной статьи загрузку и правку
  выполнить в Admin. Сохранить прежнюю ссылку на PNG на период проверки.
  Проверить статью и файл на production, включая мобильный
  viewport. При откате PHP сохранить таблицу и данные. Старый рендерер
  оставит текст инструкции и обычную ссылку доступными.

## Состояние реализации

Ветка `feature/documentation-screenshots` содержит хранилище вложений,
отображение в статье и защищённом предпросмотре, панель редактора и импорт
из stdin. Локальный `make ci` прошёл 451 тест. Отдельная проверка
восстановила статью и снимок из дампа мигрированной базы и сверила SHA-256.
В независимом ревью проверены границы доступа и разбор Markdown.

После подтверждения GD подключён в production CLI/FPM. Обе сборки и
`make php-production-smoke` прошли на изолированном стенде. HTTP-проверка
загрузила PNG через Admin, подтвердила WebP без потерь внутри статьи
и проверила, что старый ETag не открывает снимок после снятия статьи
с публикации. Для стенда использованы временные подсети, потому что
у локального Docker закончился пул адресов по умолчанию.

После подтверждения выпуска и выкладки встроить существующий снимок
формы регистрации в production-статью.
