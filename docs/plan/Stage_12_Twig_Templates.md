# Stage 12 — структура Twig-шаблонов

## Цель и границы

Объединить данные меню и футера, сгруппировать все публичные страницы по назначению и передавать в Twig готовые признаки уведомлений и переходов статусов. Публичные URL, SEO, тексты, формы и права остаются прежними. React Admin, схема БД, новые зависимости и E2E вне этапа.

## Шаги и критерии

1. Меню и CTA задаются в базовом layout; страницы задают только ключ активного пункта. На главной и служебных страницах активного пункта нет; оба меню одинаковы.
2. Футер главной наследуется из layout; на странице один футер.
3. Публичные шаблоны переносятся в `marketing/`, `publication/`, `legal/`, `lead/`, `errors/` с обновлением путей рендера. Маршруты и содержимое сохраняются.
4. `SITE_RULES.md` описывает ответственность страниц, секций и компонентов и явные аргументы partials через `with … only`.
5. `LeadStatus::needsNotification()` задаёт единое правило; read-model обращений содержат готовый признак и корректное описание причины спама. `PostStatusActionOptions` задаёт кнопки, согласованные с `PostStatus::canTransitionTo()`; серверная проверка сохраняется.

## Проверка

Unit: матрицы уведомлений и статусов публикаций. Integration: проекция карточки обращения. Functional: публичные маршруты, меню, футер, страницы ошибок, отсутствие session cookie, Admin обращения и публикации. E2E не требуется: пользовательские потоки и URL не меняются. После переноса: `make assets`, `make asset-version`, `make assets-check`, `make ci`, self-review и независимое Claude Code review. Браузерные ширины 320, 375, 768, 1024 и 1440 px проверяются через Playwright.
