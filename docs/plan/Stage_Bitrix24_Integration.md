# Stage: интеграция с Битрикс24 (заявки → лиды CRM)

## Цель

Обращения с сайта автоматически создаются лидами в Битрикс24. В админке появляется
раздел «Настройки» с подразделом «Битрикс24»: подключение через входящий вебхук,
проверка связи, включение/выключение отправки, состояние отправки.

Решения (согласованы 2026-11-22): назначение — заявки → лиды CRM с досылкой
неотправленных; подключение — входящий вебхук; адрес вебхука хранится в БД
зашифрованным.

## Блокер: согласие на обработку ПД

`templates/website/pages/legal/consent.html.twig` обещает: «Оператор … не передаёт их
третьим лицам». Облачный Битрикс24 обрабатывает данные по поручению оператора;
политика (`privacy.html.twig`, «Поручить обработку … с согласия субъекта») требует
для этого согласия. Пока текст согласия не изменён, передавать ПД в CRM нельзя.

Следствия для реализации:

- новая версия согласия (`LeadConsent::VERSION`) с упоминанием поручения обработки
  CRM-сервису; текст утверждает владелец/юрист, не агент;
- в CRM уходят только обращения, давшие согласие новой версии; старые обращения
  не отправляются даже при ручном повторе;
- до утверждения текста модуль можно влить выключенным: без вебхука ничего не уходит.

## Критерии приёмки

- Пункт меню «Настройки» → `/admin/settings` ведёт на `/admin/settings/bitrix24`.
- Ввод адреса вебхука: только `https://<портал>.bitrix24.<зона>/rest/<user>/<token>/`;
  при сохранении выполняется проверочный вызов; в UI адрес показывается маской
  (портал + последние 4 символа токена), полностью не выводится никогда.
- Кнопки: «Проверить подключение», «Отключить» (удаляет секрет), переключатель
  «Отправлять заявки».
- После регистрации обращения (после коммита) создаётся лид `crm.lead.add`:
  имя, телефон/email/Telegram по типу контакта, задача и ответы формы в комментарии,
  UTM, ссылка на карточку в админке, `ORIGINATOR_ID=vashfindir.ru`, `ORIGIN_ID=<id обращения>` (поиск с точным совпадением `=`).
- Спам и обращения со старой версией согласия не отправляются.
- Сбой Битрикс24 не влияет на сохранение обращения и ответ формы (таймаут 4 с).
- Повтор не создаёт дубль: перед повторным `add` после неизвестного исхода
  проверяется `crm.lead.list` по `ORIGINATOR_ID`/`ORIGIN_ID`.
- Досылка: команда `app:lead:export-crm-pending` (окно 7 дней, лимит 50) и кнопка
  в карточке обращения.
- Ошибки сохраняются категорией (`timeout`, `http_401`, код ошибки Битрикс24),
  без адреса вебхука и ПД; адрес не попадает в логи.

## Архитектура (реализовано)

Зависимость одна: `Lead → Bitrix24`. Модуль Bitrix24 не знает об обращениях,
поэтому цикла нет и событие не нужно (EventListener по deptrac не вызывает сервисы).

Модуль `site/src/Bitrix24/` — подключение к порталу:

- `Entity/Bitrix24Connection` → таблица `bitrix24_connection`, одна строка (`CHECK id = 1`):
  шифротекст вебхука, портал, маска, `enabled`, время и результат проверки;
- `ValueObject/WebhookUrl` — разбор и проверка адреса, `mask()`; `Bitrix24FailureReason` — подписи сбоев;
- `Adapter/WebhookCipher` — libsodium secretbox, ключ из `APP_SECRET` (generichash с контекстом);
  новый env и Production Gate не нужны; смена `APP_SECRET` → «подключите вебхук заново»;
- `Adapter/Bitrix24Client` — `crm.lead.fields` (проверка), `crm.lead.list`, `crm.lead.add`;
  таймаут 4 с, без редиректов, наружу только категория сбоя;
- `Service/Bitrix24ConnectionUpdater` — подключить (только после успешной проверки), проверить,
  включить/выключить, отключить;
- `Service/Bitrix24LeadSender` + `DTO/CrmLeadData` — публичный вход для других модулей;
- `Query/Bitrix24Settings`, `Controller/Admin/Bitrix24SettingsController`,
  `templates/admin/settings/bitrix24.html.twig`; `/admin/settings` → редирект (Admin).

Модуль Lead хранит состояние передачи у себя, как `notifiedAt` для Telegram:
`lead_lead.crm_lead_id`, `crm_exported_at`, `crm_export_error`.

- `LeadConsent::crmTransferVersions()` — пустой список: пока ничего не уходит;
- `Lead::needsCrmExport()`, `markCrmExported()`, `markCrmExportFailed()`;
- `Service/LeadCrmExporter` — сборка `CrmLeadData`, запись результата; первая попытка из
  `LeadRegistrar` после коммита, повтор (команда, кнопка) сначала ищет лид по `ORIGIN_ID`;
- `Command/ExportPendingLeadsToCrmCommand` (`app:lead:export-crm-pending`), кнопка
  «Передать в Битрикс24» и статус в карточке обращения.

## Риск и проверки

Риск высокий: секрет, отправка ПД во внешний сервис, миграция (только добавление
таблиц). Production Gate не затрагивается.

- Unit: шифр (round-trip, чужой ключ, порча), разбор/валидация адреса вебхука, маска,
  маппинг обращения в поля лида.
- Integration: экспорт на реальной тестовой БД с MockHttpClient — успех, сбой,
  таймаут, повтор без дубля, спам и старое согласие не уходят, каскад при удалении.
- Functional: `/admin/settings*` — 302 на логин без сессии, CSRF на POST, валидация
  адреса, маска в HTML, отсутствие полного адреса в ответе.
- `make ci`, `make ds-check`, браузерная проверка экрана на 320–1440px.
- Независимое ревью перед релизом (AGENTS §14.7).

## Вне объёма

Обратная синхронизация статусов, OAuth-приложение, коробочный Битрикс24 (self-hosted),
выбор ответственного/воронки, удаление лида в CRM при удалении обращения на сайте
(срок хранения 3 года на сайте не распространяется на копию в CRM — нужен отдельный
регламент).

## Независимое ревью (2026-11-22)

Блокеров и high нет. Исправлено:

- параллельная передача одного обращения (кнопка, cron, регистрация) могла создать два лида —
  сессионная advisory-блокировка PostgreSQL на обращение, досылка пропускает обращения моложе 2 минут;
- поиск лида — фильтр с точным совпадением `=ORIGINATOR_ID` / `=ORIGIN_ID`;
- HttpClient пишет полный URL в лог уровня info (виден при `-vv`) — отдельный клиент без логгера;
- SSRF — белый список зон bitrix24 и `NoPrivateNetworkHttpClient`.

Отклонено: перехват любых исключений вокруг экспорта в `LeadRegistrar`. Ожидаемые сбои CRM
уже перехватываются; прочие (сбой БД) ведут себя как у уведомления Telegram, повтор формы
дедуплицируется по `submissionId`, данные не теряются.

Ограничение: `ORIGIN_ID` — id обращения в БД; тестовый стенд не подключать к боевому порталу.
