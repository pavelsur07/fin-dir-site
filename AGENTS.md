# AGENTS.md

## 1. Назначение проекта

Проект разрабатывается как простой модульный монолит на Symfony.

Основные цели архитектуры:

- сохранять понятную структуру по мере роста проекта;
- разделять бизнес-логику по самостоятельным бизнес-модулям;
- не вводить сложность до появления подтверждённой бизнес-задачи;
- чётко разделять UI-зоны: `Public Website` рендерится Symfony/Twig, административный раздел реализуется отдельным React-приложением;
- сохранять Symfony единственным владельцем бизнес-логики, данных, authentication и authorization;
- допускать последующее подключение отдельных сервисов на Python или Go только при подтверждённой необходимости;
- запускать и развёртывать проект через Docker Compose.

## 2. Технологический стек

Основное Symfony-приложение:

- PHP 8.4+;
- Symfony 7.x;
- Doctrine ORM;
- PostgreSQL;
- Twig — единственный серверный rendering layer публичного сайта (`Public Website`);
- Symfony Forms и Validator;
- Symfony Security — authentication, authorization и серверные сессии;
- Tailwind CSS 4.x — базовый UI framework публичного сайта, разрешённый в рамках правил `SITE_RULES.md`; exact build version должна быть pinned;
- Symfony UX / Stimulus и Twig Components — для локальной интерактивности и переиспользуемых UI-компонентов публичного сайта, когда это действительно требуется.

Административный frontend:

- React — отдельное приложение административного раздела;
- React является presentation layer и не владеет бизнес-логикой или данными;
- backend административного раздела реализуется в Symfony через JSON HTTP endpoints;
- authentication выполняется Symfony Security через серверную session cookie;
- JWT/Bearer tokens не использовать по умолчанию и не вводить без отдельного архитектурного решения.

По мере необходимости:

- Symfony Messenger — фоновые и асинхронные задачи;
- Redis — очереди, блокировки, rate limit и кеш;
- Python — ML, аналитика и специализированная обработка данных;
- Go — высоконагруженные сетевые или потоковые задачи.

Инфраструктура:

- Docker;
- Docker Compose;
- Nginx;
- Traefik;
- отдельные PHP FPM и CLI-образы.

Не добавлять новые технологии, frontend-framework, state-management library, API layer или инфраструктурный компонент без конкретной задачи и зафиксированной причины.

## 4. Структура Symfony-приложения

Первый уровень в `site/src/` — бизнес-модули, а не технические слои.

```text
site/src/
├── User/
├── Publication/
├── Partner/
├── Shared/
└── Kernel.php
```

Названия модулей должны описывать бизнес-возможности проекта. Не использовать абстрактные названия вроде `Core`, `Common`, `Manager` или `Main`.

Базовая структура модуля:

```text
ModuleName/
├── Controller/
├── Entity/
├── Repository/
├── Service/
├── DTO/
├── Form/
├── Validator/
├── Security/
├── Message/
├── MessageHandler/
└── Exception/
```

Создавать только те папки, которые уже нужны. Новый модуль может начинаться с нескольких классов:

```text
Publication/
├── Entity/
│   └── Post.php
├── Repository/
│   └── PostRepository.php
└── Service/
    └── PostPublisher.php
```

Если модуль существенно вырос, сначала разделить его на внутренние бизнес-подразделы:

```text
Publication/
├── Post/
├── Category/
└── Author/
```

Слои `Domain/Application/Infrastructure/UI` вводить только локально в действительно сложном модуле. Не переводить весь проект на такую структуру без необходимости.

## Public Website

Для всех изменений публичного сайта агент обязан полностью прочитать и соблюдать:

- `SITE_RULES.md`.

`SITE_RULES.md` — Source of Truth для design system, design tokens, typography,
spacing, Twig-структуры, UI components, section architecture, CSS, responsive,
accessibility baseline и AI-generated UI anti-patterns публичного сайта.

Архитектурные ограничения Public Website:

- публичные страницы рендерятся Symfony/Twig;
- React на Public Website запрещён без отдельного архитектурного решения;
- Tailwind является единственным CSS framework Public Website; Bootstrap запрещён для нового и изменяемого website code;
- exact Tailwind version и build/runtime rules определяются `SITE_RULES.md`;
- локальную client-side интерактивность реализовывать минимально достаточными средствами, предпочтительно Stimulus/обычным JavaScript в рамках принятого frontend-стека;
- переиспользуемые визуальные элементы оформлять как Twig Components или существующие компоненты `SITE_RULES.md`, а не копировать markup между страницами;
- Twig не выполняет Doctrine-запросы, не содержит бизнес-правила и не изменяет состояние приложения;
- анонимная публичная страница не должна стартовать PHP session без конкретной необходимости;
- публичные GET-страницы проектировать cache-friendly и не добавлять персонализацию, блокирующую HTTP/CDN cache, без бизнес-причины;
- изменение существующего публичного URL после публикации требует сохранения корректного redirect, если старый URL уже мог быть проиндексирован или использован;
- не создавать новые UI patterns, произвольные стили, дубли компонентов или декоративные варианты, противоречащие `SITE_RULES.md`.

## Admin React

Административный раздел является отдельным React-приложением в `frontend/`. Symfony остаётся backend и единственным security boundary.

Базовая схема:

```text
Browser / React Admin
        ↓ same-origin HTTP + session cookie
Symfony Admin API
        ↓
Application / Query / Domain
        ↓
Doctrine / PostgreSQL
```

Правила границы React ↔ Symfony:

- React отвечает за rendering, navigation, client-side state, UX форм и отображение ошибок;
- Symfony отвечает за authentication, authorization, validation, бизнес-правила, транзакции, persistence и интеграции;
- React не подключается к PostgreSQL, Redis или внутренним сервисам напрямую;
- React не дублирует серверные бизнес-правила и правила доступа;
- client-side route guard используется только для UX и не считается проверкой прав;
- каждый защищённый endpoint повторно проверяет права на стороне Symfony;
- административный API возвращает DTO/read-model, а не сериализует Doctrine Entity целиком по умолчанию;
- входные данные административного API проходят Symfony Validator;
- state-changing HTTP endpoints должны иметь явно определённую семантику, validation и защиту от CSRF.

Session authentication:

- использовать Symfony Security и серверную сессию;
- session identifier хранится только в cookie, которую React не должен читать или копировать в browser storage;
- production session cookie должна использовать безопасные cookie attributes (`HttpOnly`, `Secure` и подходящий `SameSite`);
- React не сохраняет auth token, session id или пароль в `localStorage`/`sessionStorage`;
- JWT, access token или refresh token не добавлять параллельно session auth «на будущее»;
- logout должен завершать/инвалидировать серверную сессию;
- unauthenticated запрос возвращает `401`, authenticated без права — `403`;
- state-changing requests защищать CSRF-механизмом, совместимым с выбранным Symfony authenticator/API contract;
- предпочтительно держать React Admin и Symfony API на одном origin; CORS не включать без необходимости;
- перенос Admin на отдельный origin/domain требует отдельного решения по CORS, cookies, CSRF и session policy до реализации.

Routing и API:

- маршруты Admin UI и Admin API должны иметь явную, непересекающуюся область;
- если проектом не установлено иное, использовать единый стабильный prefix для административного API, например `/admin/api`;
- не смешивать JSON API endpoints с Twig rendering в одном action;
- публичный Website не должен зависеть от сборки React Admin.

## 6. Правила модульности

### 6.1. Владелец данных

Каждая сущность и таблица принадлежат одному бизнес-модулю.

- модуль отвечает за правила изменения своих данных;
- другой модуль не должен произвольно изменять его сущности;
- изменение выполняется через явно названный сервис или публичный сценарий модуля;
- бизнес-логика не дублируется в нескольких модулях или сервисах.

### 6.2. Зависимости между модулями

Прямые зависимости допустимы, пока они просты, понятны и не создают цикл.

Добавлять интерфейс, DTO, событие или сообщение, если:

- появилась циклическая зависимость;
- внутреннее устройство одного модуля начинает протекать в другой;
- требуется несколько реализаций;
- обработка должна стать асинхронной;
- модуль планируется реально отделить в сервис.

Не создавать интерфейс для каждого класса «на будущее».

Циклические зависимости запрещены:

```text
Publication → Partner → Publication
```

При возникновении цикла использовать сервис-координатор верхнего уровня или событие.

### 6.3. Shared

В `Shared` размещаются только общие технические примитивы без конкретного бизнес-владельца:

- Money;
- DateRange;
- Identifier;
- Clock;
- общие Doctrine-типы;
- базовые технические исключения.

Не переносить класс в `Shared` только потому, что он используется в двух местах. `Shared` не должен превращаться в склад несвязанного кода.

### 6.4. Doctrine и база данных

На старте использовать:

- одну PostgreSQL;
- одну систему Doctrine migrations;
- внешние ключи для обеспечения целостности;
- транзакции там, где нужна атомарность бизнес-операции.

Правила:

- у каждой таблицы должен быть понятный модуль-владелец;
- модуль напрямую записывает только в свои таблицы;
- внутри модуля обычные Doctrine associations допустимы;
- между потенциально отделяемыми модулями предпочтительны идентификаторы и публичные DTO;
- не отказываться от внешних ключей ради гипотетического перехода к микросервисам.

Для наглядности допустимы префиксы таблиц:

```text
user_user
publication_post
publication_category
partner_partner
```

### 7.2. DTO, ViewModel и границы передачи данных

DTO не является обязательным для каждой передачи данных внутри приложения.

Главный принцип:

> Использовать DTO на системных границах и для сложных моделей представления.
> Не создавать DTO только ради передачи нескольких простых значений в Twig.

#### Public Website / Twig

Для простых Twig-страниц разрешено передавать именованные переменные непосредственно через `render()`:

```php
return $this->render('website/pages/about.html.twig', [
    'title' => $title,
    'description' => $description,
]);
````

Это предпочтительный вариант, если страница использует небольшой набор простых значений и отдельный объект представления не даёт практической пользы.

Не создавать отдельный DTO только ради:

* `title`;
* `description`;
* `canonicalUrl`;
* нескольких простых scalar-значений;
* статического или почти статического контента страницы.

Для сложной динамической страницы использовать отдельный `View DTO` / `ViewModel`.

Пример:

```text
Controller
    ↓
Query / Application Service
    ↓
ArticlePageView
    ↓
Twig
```

`View DTO` рекомендуется, если представление:

* объединяет данные нескольких сущностей или источников;
* содержит вычисленные значения;
* имеет вложенную структуру;
* используется несколькими компонентами страницы;
* требует отдельной read-model;
* начинает передавать в Twig большое количество несвязанных переменных.

Twig не должен самостоятельно строить сложную модель страницы.

Запрещено переносить в Twig:

* Doctrine-запросы;
* бизнес-правила;
* существенные вычисления;
* получение данных из внешних API;
* изменение состояния приложения.

#### Query и списки

Для сложных списков и read-сценариев предпочтителен поток:

```text
Controller
    ↓
Query
    ↓
Projection / View DTO
    ↓
Twig
```

Query должен получать только данные, необходимые конкретному представлению.

Не загружать полную Entity и связанные коллекции, если странице требуется только ограниченный набор полей.

Для простого сценария передача Entity в Twig допустима, если:

* Entity уже загружена для данного сценария;
* не происходит скрытой загрузки большого object graph;
* Twig не использует Entity для выполнения бизнес-логики;
* это не создаёт проблем производительности или связанности.

Не вводить Projection/DTO формально, если обычная передача Entity остаётся простой и очевидной.

#### Request DTO

`Request DTO` использовать, когда входные данные образуют самостоятельную команду или контракт приложения.

Предпочтительный поток:

```text
HTTP Request
    ↓
Request DTO
    ↓
Validation
    ↓
Application Service / Handler
```

Request DTO обязателен для JSON API React Admin.

Для простой Symfony Form допустимо использовать отдельный form/input DTO.

Не использовать Doctrine Entity как внешний request-контракт API.

#### React Admin API

Граница между React Admin и Symfony является строгим API-контрактом.

Использовать:

```text
React
    ↓ JSON
Request DTO
    ↓
Application
    ↓
Domain / Doctrine
    ↓
Response DTO
    ↓ JSON
React
```

Для React Admin обязательно:

* входные JSON-данные преобразуются в Request DTO;
* Request DTO валидируется до выполнения бизнес-сценария;
* API возвращает Response DTO / read-model;
* структура API-контракта не зависит напрямую от Doctrine Entity;
* изменение Entity не должно автоматически изменять JSON API.

Запрещено:

```text
Doctrine Entity
    ↓ serialize
JSON
    ↓
React
```

Не сериализовать Doctrine Entity напрямую как публичный API response.

Причины:

* утечка внутренних полей;
* случайная загрузка associations;
* нестабильный API-контракт;
* coupling React с моделью persistence;
* проблемы с security и permissions;
* сложность последующего изменения Entity.

#### Response DTO

Response DTO должен содержать только данные, необходимые потребителю.

Не создавать универсальные DTO вида:

```text
EntityDto
FullUserDto
EverythingDto
```

если разные сценарии требуют разный набор данных.

Предпочтительно использовать DTO по конкретному назначению:

```text
PostListItem
PostDetails
PostEditData
UserSummary
PublicationPageView
```

DTO именуется по роли в сценарии, а не просто по имени Entity.

#### DTO не является бизнес-моделью

DTO:

* не содержит бизнес-правила;
* не управляет Entity;
* не обращается к Repository;
* не выполняет внешние запросы;
* не содержит инфраструктурную логику.

DTO может содержать простое структурирование данных, необходимое для представления или контракта.

Бизнес-поведение остаётся в соответствующих Entity, Application Service или Domain Service согласно `PATTERNS.md`.

#### Общий критерий

Перед созданием нового DTO агент обязан ответить на вопрос:

> DTO создаёт явную полезную границу или только добавляет дополнительный класс?

Если отдельной границы, контракта или read-model нет — DTO создавать не требуется.

Цель правила — сохранить явные контракты там, где они необходимы, не превращая простое Symfony/Twig-приложение в систему из формальных DTO для каждого значения.

```

Я бы **именно так и зафиксировал**: не правило «всё через DTO», а правило **«DTO на границах, ViewModel для сложного представления, простые Twig-переменные — без лишней обёртки»**. Это защитит проект одновременно и от хаоса, и от переархитектуривания.
```


### 7.3. Изменения схемы данных

- Все изменения структуры БД оформлять Doctrine migration.
- Миграция должна быть безопасна для существующих данных.
- Опасное удаление столбцов или таблиц выполнять отдельным этапом после переходного периода.
- Не редактировать уже применённые production-миграции.
- Для обязательного нового поля предусматривать заполнение существующих строк до добавления `NOT NULL`.

### 7.4. Интеграции и фоновые задачи

Для внешних API предусматривать:

- timeout;
- обработку ошибок;
- ограниченные retry;
- идемпотентность;
- логирование без секретов;
- защиту от повторной обработки;
- понятное поведение при недоступности сервиса.

Symfony Messenger использовать, если операция:

- выполняется долго;
- может быть повторена;
- не должна блокировать HTTP-запрос;
- требует отдельного масштабирования worker.

Не добавлять очередь для простого синхронного сценария без практической причины.

### 7.5. Публикуемый контент, URL и SEO

Если появляется блог, портал, кейсы, база знаний или другой управляемый публикуемый контент:

- бизнес-владельцем контента остаётся соответствующий Symfony-модуль, например `Publication`;
- публичные Query обязаны явно исключать draft/unpublished content;
- если у сущности есть полноценный lifecycle публикации, использовать явный status (`DRAFT`, `PUBLISHED`, `ARCHIVED` или актуальный для модели набор), а не наращивать набор несвязанных boolean-флагов;
- `publishedAt` хранить отдельно от `createdAt` и `updatedAt`, когда дата публикации имеет бизнес-смысл;
- `slug` является отдельным стабильным атрибутом и не вычисляется на каждом запросе из текущего title;
- изменение URL ранее опубликованного материала должно учитывать `301` redirect со старого URL;
- canonical, robots и meta-данные формируются явно и не должны зависеть от случайной логики Twig;
- не строить универсальную CMS или сложную taxonomy «на будущее» — добавлять типы контента, категории и связи по реальным сценариям.

### 7.6. Публичные формы и lead-сценарии

Для публичных форм:

- Request принимается через отдельный Form/DTO/input model;
- Symfony Validator выполняет server-side validation независимо от browser validation;
- не привязывать публичную форму напрямую к Doctrine Entity по умолчанию;
- после validation вызывать явно названный Application Service/Handler;
- отправку во внешние CRM, email, Telegram и другие интеграции не выполнять из Twig или Entity;
- фоновые сообщения использовать только если внешняя операция действительно не должна блокировать HTTP request или требует retry;
- повторная отправка формы и интеграционный retry не должны создавать неконтролируемые дубли, если сценарий имеет риск повторной обработки.

## 8. Python, Go и границы React

Основная бизнес-логика и владение данными остаются в Symfony, пока не принято отдельное архитектурное решение.

Отдельный сервис разрешён, если есть подтверждённая причина:

- нужной библиотеки нет или она существенно хуже в PHP;
- требуется независимое масштабирование;
- необходима изоляция ресурсоёмких вычислений или сбоев;
- нужен отдельный цикл релиза;
- нагрузка или тип задачи обоснованно требуют другого языка.

Перед выделением сервиса должны быть определены:

- владелец данных;
- API или контракт сообщения;
- версионирование контракта;
- timeout и retry;
- идемпотентность;
- healthcheck;
- журналирование;
- поведение при недоступности.

Запрещено:

- давать нескольким сервисам право независимо изменять одни и те же данные;
- подключать отдельный сервис напрямую к таблицам Symfony без обоснованного решения;
- дублировать одну бизнес-логику на PHP и другом языке.

React используется только как административный frontend в `frontend/`.

Ограничения:

- не добавлять React в Public Website или `site/templates/website/`;
- не использовать React как альтернативный backend/business layer;
- не переносить server-side authorization в React;
- не давать React прямой доступ к БД, Redis или внутренним сервисам;
- не вводить второй независимый auth-механизм для Admin;
- расширение React за пределы Admin требует отдельного архитектурного решения.

## 9. Docker и production

Основные сервисы:

```text
site                 Nginx, единственная внешняя точка входа
site-php-fpm         Symfony HTTP runtime
site-php-cli         одноразовые команды и миграции
site-worker          Messenger worker, когда появятся очереди
site-scheduler       плановые команды, когда они понадобятся
postgres             база данных, если она не внешняя
redis                очередь, блокировки, rate limit и кеш
```

Правила:

- наружу публикуется только Nginx через Traefik;
- PHP, PostgreSQL, Redis и внутренние сервисы доступны только во внутренней сети;
- контейнеры обращаются друг к другу по имени Compose-сервиса;
- не использовать `container_name` без вынужденной причины;
- не использовать изменяемый тег `latest` в production;
- все контейнеры одного релиза используют образы из одного commit SHA;
- production-образ не должен зависеть от bind mount с исходным кодом;
- конфигурация и секреты передаются через environment или secrets и не коммитятся;
- для постоянных сервисов добавляются healthcheck;
- `depends_on` не считать проверкой готовности приложения;
- CLI-контейнер использовать для одноразовых команд через `docker compose run --rm`;
- миграции выполнять отдельным контролируемым шагом релиза;
- React Admin собирать до production deployment в статические assets;
- не держать Node.js runtime в production только ради выдачи React Admin, если нет отдельной подтверждённой SSR/server-side задачи;
- Nginx остаётся единственной внешней точкой входа и обслуживает Public Website, статическую сборку Admin и проксирование Symfony endpoints;
- routing Admin UI не должен перехватывать routes административного API;
- не запускать разрушительные команды и миграции без явного production gate.

Основной production-файл:

```text
docker-compose.prod.yml
```

Не изменять production-инфраструктуру в рамках обычной бизнес-задачи, если это не входит в её согласованный объём.

## 10. Принципы изменений

При выполнении задачи агент обязан:

- решать только поставленную задачу;
- сначала изучить затрагиваемый код, конфигурацию и тесты;
- сохранять существующий стиль проекта;
- выбирать минимальное достаточное изменение;
- не выполнять широкий рефакторинг без необходимости;
- не переименовывать и не перемещать несвязанные классы;
- не менять публичные контракты без явной причины;
- сохранять обратную совместимость, если её нарушение не согласовано;
- не добавлять пакет, технологию, слой или паттерн без доказанной пользы;
- не исправлять несвязанные проблемы молча;
- явно сообщать об обнаруженных проблемах вне объёма задачи.

При противоречии между этим файлом, техническим заданием и фактическим кодом агент должен остановиться в спорной части, описать противоречие и запросить решение.

## 11. Рабочий процесс агента

Работа выполняется автономно на уровне согласованного этапа. Внутри этапа агент не запрашивает подтверждение каждого локального, обратимого действия, если оно не выходит за согласованный объём и не требует Production Gate.

Этап считается завершённым только после выполнения полного цикла:

```text
подробный план
→ чек-лист готовности
→ реализация
→ тесты
→ self-review
→ исправления
→ Claude Code review
→ исправления
→ повторные тесты
→ отчёт
```

### 11.1. Анализ задачи и подробный план

До изменения кода агент обязан:

1. Прочитать задачу, критерии приёмки и ограничения.
2. Найти локальные инструкции проекта и документацию по затрагиваемому модулю.
3. Изучить текущую реализацию, связанные сценарии, тесты и историю решений, доступную в репозитории.
4. Проверить состояние Git и не затрагивать чужие незавершённые изменения.
5. Определить границы задачи и явно зафиксировать, что в неё не входит.
6. Оценить влияние на бизнес-логику, Public Website/Twig, Admin React, session authentication, CSRF, права доступа, видимость публикаций, схему БД, интеграции, очереди и публичные контракты.
7. Подготовить подробный поэтапный план до начала реализации.

План должен содержать:

- цель и ожидаемый результат;
- проверяемые критерии приёмки;
- затрагиваемые модули и предполагаемые точки изменения;
- последовательность небольших логически завершённых шагов;
- зависимости между шагами;
- изменения данных и миграции, если они требуются;
- риски, граничные случаи и требования обратной совместимости;
- тестовую стратегию по уровням `unit`, `integration`, `functional`, `e2e`;
- проверки качества и команды, которыми будет подтверждён результат;
- критерии завершения каждого шага и всего этапа.

План является рабочим документом. Если во время реализации обнаружены новые факты, агент обновляет план и продолжает работу, пока изменение остаётся в согласованных границах. Если требуется существенное изменение бизнес-логики, архитектуры или объёма, действуют правила остановки.

### 11.2. Чек-лист готовности к реализации

Перед изменением кода агент проверяет Readiness Gate:

- [ ] цель задачи и пользовательский результат понятны;
- [ ] критерии приёмки конкретны и проверяемы;
- [ ] границы этапа и исключения зафиксированы;
- [ ] затрагиваемый код и существующие тесты изучены;
- [ ] зависимости и владельцы данных определены;
- [ ] права доступа и видимость неопубликованных данных учтены;
- [ ] определено, относится изменение к Public Website/Twig, Admin React, Symfony Admin API или нескольким границам сразу;
- [ ] для Admin учтены session auth, `401/403`, CSRF и server-side authorization, если применимо;
- [ ] влияние на БД, миграции и существующие данные оценено;
- [ ] обратная совместимость и публичные контракты проверены;
- [ ] внешние интеграции, timeout, retry и идемпотентность учтены, если применимо;
- [ ] для каждого уровня тестирования определено покрытие либо обосновано `N/A`;
- [ ] понятны команды запуска тестов и проверок;
- [ ] отсутствуют блокирующие противоречия и недостающие решения.

Если обязательный пункт не выполнен, агент сначала устраняет пробел самостоятельно. Запрос пользователю нужен только тогда, когда отсутствующее решение нельзя безопасно вывести из задачи, кода или правил проекта.

### 11.3. Реализация этапа

1. Выполнять план последовательно небольшими проверяемыми изменениями.
2. Реализовывать минимально достаточное решение без несвязанного рефакторинга.
3. Добавлять или обновлять тесты одновременно с изменяемым поведением.
4. После каждого логического шага запускать наиболее узкий релевантный набор тестов.
5. После завершения реализации этапа запускать весь согласованный набор проверок.
6. Не переходить к ревью с заведомо падающими релевантными тестами.

### 11.4. Стратегия тестирования

Для каждого этапа агент обязан рассмотреть все четыре уровня тестирования:

| Уровень | Что проверяет | Когда обязателен |
|---|---|---|
| `Unit` | Бизнес-правила, value objects, вычисления и отдельные сервисы без инфраструктуры | При добавлении или изменении изолируемой бизнес-логики |
| `Integration` | Doctrine repositories, БД, миграции, сериализацию, Messenger и адаптеры интеграций | При изменении взаимодействия с инфраструктурой |
| `Functional` | HTTP/API/Console-сценарий через Symfony kernel, валидацию, security и итоговый ответ | При изменении пользовательского или системного сценария |
| `E2E` | Критический поток через реальные границы системы в тестовом окружении | Для критичных сквозных сценариев и изменений с высоким регрессионным риском |

Не требуется механически создавать тест каждого уровня для любого изменения. В плане и итоговом отчёте каждый уровень должен быть отмечен одним из вариантов:

- добавлен или обновлён;
- покрыт существующим тестом с указанием набора;
- `N/A` с конкретным объяснением, почему уровень не относится к изменению.

Основные правила:

- тестировать наблюдаемое поведение, а не внутреннюю реализацию;
- один тест должен проверять один понятный сценарий;
- обязательно покрывать основной сценарий, ошибки, граничные значения и контроль доступа;
- для исправления дефекта сначала добавлять воспроизводящий regression test;
- тесты должны быть детерминированными и независимыми от порядка запуска;
- не обращаться из обычных тестов к production-сервисам;
- не заменять интеграционный тест набором mock-объектов, если риск находится на границе с БД или фреймворком;
- количество тестов и их уровень определять по риску изменения, а не ради формального процента покрытия.

Дополнительно для Public Website:

- иметь smoke coverage основных публичных routes;
- при изменении публикаций проверять недоступность draft и доступность published content;
- при изменении URL проверять redirect semantics;
- при изменении публичной формы проверять validation, успешную отправку и ошибочный сценарий;
- при изменении SEO/cache поведения проверять итоговые HTTP headers/meta там, где это является частью задачи.

Дополнительно для Admin React:

- запускать настроенные frontend lint, tests и production build для затронутого frontend-кода;
- server-side Functional tests должны проверять session authentication, authorization и `401/403` для защищённых API endpoints;
- state-changing endpoints тестировать с учётом CSRF-механизма, если он применим к выбранному контракту;
- критические admin flows (login/logout, доступ к защищённому разделу, ключевые операции с правами) покрывать E2E по риску;
- косметическое изменение React-компонента само по себе не требует нового E2E, если критический поток уже покрыт и не изменён.

### 11.5. Test Data Builder

Для подготовки тестовых данных использовать паттерн `Test Data Builder`.

Вспомогательные builder-классы размещать только в тестовом коде:

```text
site/tests/
├── Support/
│   └── Builder/
└── Publication/
    └── Builder/
```

Выбор расположения:

- `tests/<Module>/Builder/` — builder используется одним бизнес-модулем;
- `tests/Support/Builder/` — builder действительно используется несколькими модулями.

Правила builder-классов:

- создавать валидный объект с безопасными значениями по умолчанию;
- предоставлять явно названные методы изменения значимых полей, например `withTitle()` или `published()`;
- завершать построение методом `build()`;
- не скрывать в `build()` неожиданные внешние вызовы, время системы или случайные значения;
- позволять тесту явно задать идентификатор, дату и другие значения, влияющие на результат;
- не переносить тестовый builder в production-код;
- не создавать универсальный builder для несвязанных сущностей;
- не дублировать в builder бизнес-правила production-кода.

Создание объекта и сохранение в БД по возможности разделять:

```text
PostBuilder::aPost()->withTitle(...)->published()->build()
TestEntityPersister->persist($post)
```

Для короткого и очевидного набора данных отдельный builder не обязателен. Builder добавляется, когда он уменьшает дублирование, делает сценарий понятнее или позволяет безопасно собирать сложный валидный объект.

### 11.6. Обязательный self-review

Проверить:

- соответствует ли результат критериям приёмки;
- выполнен ли план и закрыт ли чек-лист готовности;
- не вышло ли изменение за границы задачи;
- не появилась ли циклическая зависимость;
- не продублирована ли бизнес-логика;
- корректны ли права доступа и видимость неопубликованных данных;
- не перенесены ли security/business rules из Symfony в React;
- не появился ли второй auth-механизм, token storage или нарушение session/CSRF boundary;
- не стартует ли публичный сайт session без необходимости;
- безопасны ли миграции;
- обработаны ли ошибки и граничные случаи;
- отсутствуют ли секреты и чувствительные данные;
- добавлены ли достаточные тесты;
- не нарушена ли обратная совместимость.

Self-review проводится после завершения реализации как ревью чужого кода:

1. Повторно прочитать задачу и критерии приёмки.
2. Просмотреть полный diff, а не только отдельные изменённые файлы.
3. Проверить корректность архитектуры, поведения, тестов, миграций и обработки ошибок.
4. Зафиксировать замечания по степени риска.
5. Исправить все блокирующие и относящиеся к задаче замечания.
6. Повторно запустить затронутые тесты и проверки.

Self-review не считается выполненным, если агент только перечитал написанный код без просмотра полного diff и повторной проверки критериев приёмки.

### 11.7. Обязательное ревью через Claude Code

После успешного self-review и зелёных релевантных тестов агент обязан провести независимое ревью этапа с помощью Claude Code.

В Claude Code передаются:

- исходная задача и критерии приёмки;
- границы этапа;
- подробный план;
- полный diff этапа;
- сведения о выполненных тестах и проверках;
- известные риски и пункты `N/A`.

Claude Code должен работать как независимый reviewer и проверить:

- соответствие требованиям;
- ошибки бизнес-логики и граничные случаи;
- архитектурные и межмодульные зависимости;
- security, права доступа и видимость неопубликованных данных;
- целостность данных и безопасность миграций;
- обработку ошибок, retry и идемпотентность;
- достаточность и качество тестов;
- обратную совместимость;
- избыточную сложность и несвязанные изменения.

Порядок обработки результата:

1. Классифицировать замечания как `blocker`, `high`, `medium`, `low` или `non-actionable`.
2. Исправить все обоснованные `blocker`, `high` и относящиеся к задаче `medium`.
3. Для отклонённого замечания зафиксировать краткое техническое обоснование.
4. Повторно запустить релевантные тесты после исправлений.
5. При существенных изменениях повторить Claude Code review.
6. Не считать этап завершённым, пока остаются обоснованные `blocker` или `high`.

Claude Code используется только для ревью и не должен самостоятельно изменять код в рабочей ветке. Запускать его через настроенный в проекте способ. Если Claude Code недоступен или завершил ревью с ошибкой, агент обязан сообщить об этом и не утверждать, что внешнее ревью пройдено.

### 11.8. Проверки

Запускать проверки из контейнеров проекта, если проект рассчитан на Docker.

Минимально, в зависимости от изменения:

```bash
php bin/console lint:container
php bin/console lint:yaml config
php bin/console lint:twig templates
php bin/phpunit
make deptrac
```

`make deptrac` проверяет границы слоёв из `docs/architecture/PATTERNS.md`
и обязателен при добавлении или перемещении классов между слоями.

Дополнительно запускать настроенные в проекте:

- PHP CS Fixer или ECS;
- PHPStan или Psalm;
- Doctrine schema validation;
- frontend lint, tests и production build для React Admin;
- проверку конкретного модуля или тестового набора.

Не утверждать, что тесты прошли, если они не запускались. Если проверка невозможна, указать точную причину и непроверенный риск.

### 11.9. Чек-лист завершения этапа

Этап готов к передаче только при выполнении Definition of Done:

- [ ] критерии приёмки выполнены;
- [ ] изменение не вышло за согласованные границы;
- [ ] код и тесты реализованы;
- [ ] все четыре уровня тестирования учтены, неприменимые помечены `N/A` с причиной;
- [ ] релевантные тесты и проверки проходят;
- [ ] при изменении React Admin его lint/tests/build выполнены либо явно обоснован `N/A`;
- [ ] при изменении auth/API проверены session, authorization, `401/403` и CSRF boundary;
- [ ] полный diff проверен самостоятельно как чужой код;
- [ ] замечания self-review исправлены;
- [ ] Claude Code review выполнен;
- [ ] обоснованные замечания `blocker` и `high` закрыты;
- [ ] после исправлений тесты запущены повторно;
- [ ] миграции, риски и действия перед релизом зафиксированы;
- [ ] подготовлен итоговый отчёт.

## 12. Остановка работы

Агент обязан остановиться и уведомить пользователя, если:

- задача требует разрушительного действия, не указанного явно;
- требуется доступ к production или внешнему сервису, которого нет;
- обнаружено противоречие требований;
- необходим выбор, существенно влияющий на бизнес-логику или совместимость;
- тесты выявили проблему, которую нельзя безопасно исправить в рамках задачи;
- в затрагиваемых файлах есть конфликтующие незавершённые изменения;
- для продолжения требуется расширение согласованного объёма работ.

Сообщение об остановке должно содержать:

1. что именно остановило работу;
2. что уже выполнено;
3. какие риски остаются;
4. рекомендуемый вариант продолжения;
5. точный ответ или разрешение, которое ожидается от пользователя.

## 13. Git и релиз

- Не выполнять `commit`, `push`, merge, создание PR или deploy без явного запроса либо согласованного release-процесса.
- Не использовать разрушительные команды вроде `git reset --hard`.
- Не удалять и не перезаписывать чужие изменения.
- Один commit должен содержать одно логически завершённое изменение.
- Перед передачей в релиз должны быть пройдены релевантные тесты, self-review и Claude Code review.
- Изменения production-конфигурации, миграции с риском потери данных и необратимые операции требуют отдельного Production Gate.

## 14. Итоговый отчёт

После завершения задачи агент сообщает:

- что реализовано;
- какие файлы и модули изменены;
- какие архитектурные решения приняты;
- какие тесты и проверки запущены и их результат;
- как учтены уровни `unit`, `integration`, `functional` и `e2e`;
- результат self-review и Claude Code review;
- какие замечания исправлены или отклонены с обоснованием;
- что не проверено;
- есть ли миграции, риски или необходимые действия перед релизом.

Отчёт должен быть кратким, конкретным и не заявлять о действиях, которые фактически не выполнялись.

## 15. Главный принцип

Сначала использовать простое решение внутри Symfony-монолита и сохранять фиксированную границу UI: Public Website — Twig, Admin — React.

Symfony остаётся владельцем бизнес-логики, данных и security. Новый слой, очередь, сервис, язык или дополнительное frontend-приложение добавляются только тогда, когда существующее решение уже не удовлетворяет конкретной подтверждённой задаче.
